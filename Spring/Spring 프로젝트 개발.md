# Spring 프로젝트 개발

## 파일의 구분
### Entity (ex.Member, Order)
데이터베이스의 테이블과 1:1로 매핑되는 객체. 고유한 식별자(ID)를 가지며, 자신의 데이터와 관련된 핵심 비즈니스 규칙(상태 변경, 검증)을 직접 수행

### Enum (ex.Grade, OrderStatus)
'VIP', 'BASIC' 처럼 정해진 상수 집합을 관리하는 열거형 파일

### Service / ServiceImpl (ex.MemberService, OrderServiceImpl)
비즈니스 유스케이스(가입, 주문 등)의 실행 흐름을 관리. 말 그대로 비즈니스적인 서비스를 담당하는 메서드들이 포함됨

### Repository (ex.MemberRepository)
데이터베이스에 접근하여 데이터를 저장, 조회, 수정, 삭제하는 데이터 영속성 전담 인터페이스/클래스


## 인터페이스의 구분
### 클라이언트와 DB 연결의 구분
Spring 프로젝트를 개발할 때, 유사한 기능을 수행하더라도 클라이언트와 연결된 인터페이스와 DB와 연결된 인터페이스를 구분해야 됨. 예를들어, 클라이언트가 회원가입을 하거나 로그인을 할 때, 이를 처리하는 인터페이스와 구현체가 있을 것이고, 전달된 회원 정보를 DB에 생성하거 조회하는 역할을 수행하는 인터페이스와 구현체를 구분해야 함.

### 어디까지 인터페이스와 구현체로 구분해야하는가
실무에서 인터페이스 분리 여부를 결정하는 기준은 명확함. **이 부분의 정책/기술이 바뀔 가능성이 있는가?(변화의 가능성)** 과 **다형성이 필요한가?** 이다.

예를들어 할인정책이 고정할인에서 정률할인으로 변동될 가능성이 있기에 할인서비스는 인터페이스와 구현체로 분리하여 구현함. 결제기능 역시 카카오페이, 네이버페이 등 다형성이 필요하기 때문에 인터페이스와 구현체로 분리함

**YAGNI(You Aren't Gonna Need It)원칙** 

처음부터 모든 것에 인터페이스를 억지로 만들면 파일 개수만 늘어나고 코드 추적이 피로해짐. 
변화가 확실한 영역만 인터페이스로 만들고, 나머지는 단일 클래스로 시작한 뒤, 나중에 변경 요구가 발생했을 때 인터페이스를 추출하는 것이 실무에서 권장하는 방법


### 계산 및 로직은 어디에서 처리해야 하는가
객체 지향 설계에서는 **Information Expert 패턴** ("데이터를 가장 잘 알고 있는 객체에게 책임을 맡겨라") 과 **Tell, Don't Ask 원칙** ("묻지 말고 시켜라")을 따른다. 
> 즉, 외부에서 Getter로 데이터를 꺼내와 서비스에서 계산하기 보다는, 데이터를 쥐고 있는 **엔티티** 내부에서 직접 계산하고 상태를 바꾸는 것이 기본

## DI(Dependency Injection)
> 객체를 생성하고, 그 참조값을 인터페이스에 주입하는 역할은 AppConfig가 담당하여 OCP와 DIP를 위반하지 않을 수 있음

### 구현체의 변경
``` java
public class OrderServiceImpl implements OrderService {
//    private final DiscountPolicy discountPolicy = new FixDiscountPolicy();
private final DiscountPolicy discountPolicy = new RateDiscountPolicy();
}
```
기존의 OrderServiceImpl 파일에서 할인정책을 변경하려면 다음과 같이 새로운 할인정책 구현체를 DiscountPolicy라는 인터페이스에 new를 통해 생성하고 대입해줬어야 함

<mark>문제는 OrderServiceImpl이 DiscountPolicy(추상)에만 의존하는 것이 아니라 FixDiscountPolicy(구현체)에도 의존했었기에 DIP와 OCP를 위반한다는 것</mark>

> 애플리케이션을 하나의 공연이라 할 때, 각각의 인터페이스는 배역이고, 이를 연기하는 배우가 구현체가 된다. 근데, 위의 애플리케이션에서는 배우가 자신의 상대 배우를 결정하고 있는 상황이 발생함. 따라서 이 공연의 기획자를 만들고, 배역에 맞는 배우를 넣어주는 것을 기획자가 담당하는 방식으로 해결해야 함

### 의존관계 주입
DIP 와 OCP를 위반하지 않고 오직 추상(인터페이스)에만 의존하도록 설계를 하기 위해서는 외부에서 인터페이스와 구현객체 사이의 대입(의존관계주입)을 해주는 역할이 필요함. **AppConfig** 가 의존관계를 주입. AppConfig 파일 안에 메소드를 정의하여 각 메소드에서 구현체의 생성자를 호출하는 메소드를 만들고, 생성자를 호출할 때 전달하는 매개변수로 해당 구현체에서 사용해야 되는 상대 배우(또 다른 구현체)를 전달함.
> 즉 AppConfig라는 외부의 기획자가 필요한 구현체를 직접 넣어줌으로써 구현체 내부에서 또 다른 구현체에 의존해야 되는 상황을 방지할 수 있음.

### '사용영역'과 '구성영역'의 분리
AppConfig의 등장으로 애플리케이션이 크게 사용영역과, 객체를 생성하고 구성하는 구성영역으로 분리됨. 구성영역에 있는 AppConfig 일종의 공연 기획자가 배우들을 조율하기 때문에 배우를 바꿔야 할 때 사용영역을 건드리지 않아도 됨
